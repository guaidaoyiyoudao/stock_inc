## 二、高危问题（实测铁证，建议立即修复）

### H1. 个股资金流「张冠李戴」——clist 单股筛选失效，返回的是别的股票的数据

- **位置**：`MarketDataRepository.fetchCapitalFlow`（`app/src/main/java/com/stock/dividend/data/repository/MarketDataRepository.kt:101-121`），经 `MarketDataPlane.getCapitalFlow`（60s 缓存）供 AI 工具 `get_stock_capital_flow`（`CapitalFlowTools.kt:32`）消费。
- **实测证据**（2026-08-20，双通道复现，curl 与 WebFetch 独立验证一致）：
  - 请求 `fs=m:1+t:2+s:600941`（`+` 正确编码为 `%2B`，与 Retrofit 实际行为一致），意图取中国移动单股；
  - 实际返回 `total=1628`（**全沪市列表**），`fid=f3` 排序首条=**志邦家居 603801**，`fid=f62` 排序首条=**紫金矿业 601899**；
  - 对照组：`s:600941` / `m:1+s:600941` / `t:2+s:600941` 四种写法**全部失效**，s: 筛选均不生效。
- **代码放大器**：`fetchCapitalFlow` 取 `pz="1"` + `diff.firstOrNull()`，且 `fields` 中**无 f12**——即使想核对返回的是哪只股票都做不到。结果：`fetchCapitalFlow("sh.600941")` 实际返回「当日沪市涨幅第一名」的资金流，作为中国移动的数据展示给用户/喂给 AI。
- **影响**：AI 助手的 `get_stock_capital_flow` 工具输出完全错误的数据（主力净额/占比全是别人家的），比崩溃更隐蔽（数字看起来都合理）。
- **佐证**：`stock/get` 的 f62 实测返回 `2`（元，无效占位），印证 §4.9.3 弃用它拉资金流的动机正确，但替代方案 clist 的单股筛选从未验证过「返回的是哪只股票」——当时只验证了「字段是否齐全」。
- **修复建议**：fields 加 f12，解析后校验 `f12 == 请求代码`，不匹配返回 null；或改用东财逐分钟资金流接口（`stock/fflow/kline/get`，按 secid 单股可靠）。补「响应行归属」单测。

### H2. 腾讯分红分块窗口超 640 根上限——结构性截断洞导致分红历史丢笔（实测丢笔 11%）

- **位置**：`DividendRepository.fetchAllDividendsFromTencent`（`DividendRepository.kt:136-147`）：块1=`[today-3y, today]`，块2=`[today-6y+1d, today-3y-1d]`，`KLINE_COUNT=640`。
- **实测证据**（中国移动 600941，2026-08-20）：
  - 块1 请求 [2023-08-20, 2026-08-20]（≈730 交易日 > 640 上限）→ 实际返回 640 根，**首根=2023-12-27**（锚定最新端、截掉头部 4 个月）；
  - 块2 请求 [2020-08-19, 2023-08-19] → 返回 394 根（首根=2022-01-05 恰为该股上市日，块2 完整）；
  - **洞 = 2023-08-19 ~ 2023-12-26**：东财完整数据显示该区间内有除权日 **2023-09-01（10派22.247，2023-06-30 报告期）**，腾讯两块响应中**均无此笔**——永久丢失；
  - 中国移动 A 股上市以来实派 9 笔，腾讯主源只拿到 8 笔，**丢失率 11%**。
- **影响链**：
  1. `DividendMetricsCalculator` 分红深度（连续年数/CAGR/稳定性）——2023 年度金额少算 2.2247 元/股，CAGR/均值失真；
  2. `ForecastCalculator.calculateAvgCashPerShare`（N 年均，驱动预测收入）——滚动窗口含洞期时年均被压低；
  3. K线前复权漂移检测依赖 `MAX(exDividendDate)`——若某股**最新**除权日恰落入随时间漂移的洞内，漂移检测失明（当前 640 根 ≈2.6 年覆盖，3 年窗口注定有洞）；
  4. 历史保留式写入不会自愈（腾讯不返回的行永远不会进库，东财回退仅在腾讯**整体失败**时触发，不按笔补洞）。
- **修复建议**：块1 缩短至 2 年（<640 根安全区，与 `KlineRepository.FULL_FETCH_BARS=250` 的「不赌超窗截断」纪律对齐），块2 从 today-2y 向前 2.5 年，块间设 3 个月重叠带；`DividendRepositoryTest` 补分块参数锁定测试（当前完全未锁窗口参数）。

## 三、中危问题（机制确认，场景依赖）

### M1. clist 列表类接口「"-" 整批毒化」——一条退市/停牌记录炸掉整个列表
- **机制实证**：clist 对退市/停牌股全字段返回 `"-"`（实测按成交额升序拉全市场，前 15 只 f2/f3/f6 **全部为 "-"**：PT金田A/国华退/ST星源 等）；项目 Gson 2.11.0 实测 `"-"`→`Double` 抛 `NumberFormatException` 且**整批 diff 反序列化失败**。
- **受影响路径**：`fetchIndustryPeers`/`fetchMarketRanking`/`fetchIndustryList`（`MarketDataRepository.kt:131/157/191`）——runCatching 粒度是整个列表，一条脏记录 → 整列表空。
- **触发概率评估**：按股息率/涨幅/市值排序时 "-" 记录排尾，limit 内混入概率低-中；但行业板块成分含长期停牌股时风险实在。
- **对比修正**：agent 初判「ulist 一只停牌股毒死全部自选股行情」经实测**不成立**（ulist 对停牌股返回全 0 数值而非 "-"，Gson 不炸，0 价被正确转 null）——ulist 路径安全，风险仅集中在 clist 列表路径。
- **建议**：clist DTO 数值字段改 `String?` 手工解析（`toDoubleOrNull`）或自定义 TypeAdapter 容错；至少 per-item 粒度降级。

### M2. 双派息股派息率系统性失真（约低估一半）
- **位置**：`MarketDataPlane.kt:298-321`（`cashByReportDate` 用 `associate`，同 key **last-wins 不合计**）+ `DividendRepository.kt:114`（腾讯 `nd` 强制补成 `YYYY-12-31`，中期/末期两笔 reportDate 撞同一天）。
- **后果**：腾讯主源下，年报期 `payoutRatio = 单笔分红 ÷ 全年 EPS`（中国移动类半年派息股约低估一半），真实中期报告期（06-30）永远匹配不上（null）。与 2026-08-19 已修复的「股息率只算一半」同根不同枝——股息率路径修了，**派息率路径漏修**。
- **建议**：`cashByReportDate` 改为按报告期合计（groupBy+sum）；或腾讯源 reportDate 改用东财真实报告期对齐。

### M3. 国债收益率冷启动失败后 2.5% 默认值锁死内存缓存
- **位置**：`BondYieldRepository.kt:36,53-61`：无缓存且远端失败 → `DEFAULT_YIELD(2.5)` 写入 `memoryCache` → 进程存活期内所有非强制调用**永远返回 2.5，网络恢复不再重试**。
- **影响**：买入线（10Y×倍数）、组合诊断估值水位（利差）在断网冷启动后整个会话期用假基准。当前 10Y 真实值约 1.8-2.0%，2.5% 会系统性抬高买入门槛。
- **建议**：失败时不写 memoryCache（null=未初始化，下次重试）。

### M4. K线前复权漂移检测三缺口
- **纯送转/转增/配股不落 dividends 行**（腾讯源只写 `fh_sh>0` 现金分红行，`DividendRepository.kt:112/166`）→ 无现金公司行动造成的全历史位移**检测不到**，缓存保留错误复权基准（BOLL/网格锚定全错）直至手动强刷；
- **分红 7 天 TTL 滞后期**：除权发生后 dividends 表可能最长 7 天未刷新，期间增量补尾把除权后口径新 K 线 upsert 进除权前口径旧缓存（混合纪元序列污染 BOLL）；
- **未来除权日超前误触发**：dividends 表为日历倒计时存未来 exDate 时，`MAX(exDividendDate)` 超前导致一次性多余全量重建（浪费，非错误）。
- **建议**：K线 meta 增加送转事件比对（或腾讯 gsplit 接口）；除权检测触发点联动强制刷新分红表。

### M5. mergeByReportDate 整期覆盖是记录级而非字段级
- **位置**：`FundamentalsCacheRepository.kt:32` / `FinancialStatementsRepository.kt:37`：某次刷新资产负债表接口失败（runCatching 降级空表）→ 远端同期记录 `debtToAssetRatio=null` **整体覆盖**缓存里原本字段齐全的同期记录，且随后持久化，无法自愈。
- **建议**：merge 时字段级保底（远端 null 字段回退缓存值）。

### M6. `DividendRepository.kt:215` 裸 Gson 调用无 runCatching
- 东财回退源 `getDividends` 是全库唯一未兜底的 Gson 入口（对比 enrich 路径 :185 有包）。当前实测该接口脏值返回 null 而非 "-"，概率低，但属纪律缺口（§4.9.5-5）。

### M7. `PortfolioDiagnosisAssembler.kt:42` 新鲜度策略不一致
- 用 `plane.getDividends`（**不触发 ensureDividendsFresh**）而非 `getDps` 取 DPS：从未刷新过分红的股票在组合诊断里 annualDividend/yieldPct=null，而同会话 compare 工具却能拿到——诊断结论可能基于缺失数据。公式口径无问题，纯新鲜度差异。

### M8. `toIndexQuote`/`toMarketList` 无函数级测试（规则反转无回归锁）
- `MarketDtoParseTest.kt:152-160` 自己承认 toIndexQuote 是 private 只做「等价手工断言」**不执行生产代码**；`MarketDataRepository` 无任何函数级测试文件。若有人把 stock/get 当 clist 处理（去掉 ÷100）或反之，**没有任何测试会红**——这正是 §4.9 标记的最大易错点。clist↔ulist 规则反转 + H1 的「响应行归属」都缺测试护栏。

### M9. `fetchIndustryPeers` 的 DB 读逃逸 runCatching
- `MarketDataRepository.kt:156`（`resolveIndustryCode` → `observeStock().first()`）在 runCatching 之外，DB 异常直接冒泡调用方，违反红线 #2 精神。

> ✅ 2026-08-20 同日修复后，「不可信」清单中的前三项已转为可信（见第〇节修复状态）；剩余项为已知限制。

**剩余已知限制（修复前应知悉）**：
