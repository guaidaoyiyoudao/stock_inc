01

特性介绍

定位：阿里内部运行两年、服务数万开发者后开源的 AI 代码评审工具（CLI 命令 ocr）。核心思路是——“不许出错”的环节交给工程代码，动态理解交给 LLM，从而解决通用 AI 直审 diff 的三大痛点：大变更集覆盖不全、评论位置漂移、输出质量不稳定。

混合架构：确定性工程 × LLM

确定性工程流水线（硬约束）

  • 五道闸文件过滤：二进制 → 用户排除 → 用户包含 → 扩展名白名单 → 默认测试文件排除
  • 智能文件捆绑：相关文件打包为一个审查单元（如中英文 properties 对照审），每单元独立 sub-agent 并发
  • 模板引擎规则匹配：按文件特征细粒度匹配审查清单
  • 独立评论定位模块：系统性保证“报在哪一行”
  • 独立内容反思模块：系统性保证“报得对不对”

LLM Agent（动态决策）

  • 场景调优提示模板：针对代码评审深度优化
  • 蒸馏工具集：从大规模生产数据的工具调用轨迹统计调优（调用频率、重复率）
  • 可读完整文件、搜索代码库、查看关联变更

→ 同等模型下精度、F1 优于通用 Agent，token 消耗仅约 1/9

02

与“直接用提示词评审”的对比

基线方案：把 diff 贴给通用 AI / 编码 Agent，附加一段“你是资深工程师，请评审以下代码”的提示词。这是当前零成本最常见的做法。两者差距不在模型，而在模型外围的工程保障：

对比维度 提示词直审 open-code-review
大变更集覆盖 ✗ 上下文窗口有限，几十个文件的 diff 会被截断或选择性忽略，覆盖随规模劣化 ✓ 五道闸精确圈定范围 + 相关文件捆绑分单元，独立 sub-agent 并发，大 PR 全覆盖
评论定位 ✗ 位置漂移高发（“第 N 行附近”经常指错行），需要人工二次定位 ✓ 独立定位模块工程化保证行级准确率
输出质量稳定性 △ 取决于提示词写作水平与当日模型状态，不同人/不同次结果差异大 ✓ 场景调优提示模板 + 反思模块 + 从生产轨迹蒸馏的工具集；同模型下 Precision/F1 经基准验证
规则沉淀 ✗ 团队规范只能写进提示词口头传递，无版本、无分层、易漂移 ✓ 四层规则链：项目红线沉淀为 rule.json 随仓库提交、随 diff 生效
成本 全量上下文反复投喂，token 消耗大 约 1/9（调优提示模板 + 精确文件选择削减无效 token）
覆盖率问责 ✗ 漏审哪些文件无从知晓 ✓ 每个文件落位 reviewed / skipped（附原因），汇总含覆盖率
防刷屏 ✗ 每次全量重报 ✓ 增量评论（相似度去重）、汇总原地更新、低严重度路由
接入成本 ✓ 零（复制粘贴即用） ✓ 低（一条命令装 CLI；规则文件一次沉淀长期复用）
诚实标注：OCR 的 Recall（查全率）刻意低于通用 Agent——设计哲学是“宁可少报、不许误报”。它的定位是高置信度探测器，与单测、CI 构建、人工评审组成纵深防线，而非替代。另外，提示词直审的灵活性（随意追问、任意上下文）是它的天然优势，两者是互补关系：日常快速判断用直审，正式把关用 OCR。
03

三种接入形式的配置方法

三种形式共享同一套基础设施（CLI + 规则文件），按投入从低到高排列，可并存、可渐进：

形式LLM 来源费用适用场景
① 本地委托模式宿主 Agent 自带模型零日常自查，commit / merge 前
② Agent Skill（OCR 驱动）OCR 调用自配端点API token本地高精度正式评审
③ CI 流水线OCR 调用自配端点API tokenMR / PR 自动评审

形式 ①：本地委托模式（零配置零费用）

已完成试点 OCR 只负责文件选择与规则解析（ocr delegate preview + rule），评审由编码 Agent 在自己会话中执行——对话上下文、工作区规范天然可用，且与写码过程形成独立上下文制衡。

# 1. 安装 CLI（要求 Git ≥ 2.41）
npm install -g @alibaba-group/open-code-review

# 2. 安装官方现成 skill 到工程（ZCode/Claude Code 等通用发现路径）
mkdir -p .agents/skills/open-code-review-delegate
curl -o .agents/skills/open-code-review-delegate/SKILL.md \
  https://raw.githubusercontent.com/alibaba/open-code-review/main/plugins/open-code-review/skills/open-code-review-delegate/SKILL.md

# 3. 无需任何 LLM 配置。对 Agent 说「用委托模式评审当前改动」即触发：
#    preview 选文件 → rule 出规则 → Agent 取 diff 逐文件审 → 分级报告

审查范围支持：工作区变更（默认）/ 分支对比 / 单 commit；报告按 Critical/High/Medium 分级，Low 默认丢弃防噪。

形式 ②：Agent Skill —— OCR 驱动的本地评审

宿主 Agent 只做调度与汇报，评审由 OCR 完整管线执行——吃到智能捆绑、定位模块、反思模块的全部工程红利，精度最高。需配置 LLM 端点（任意 OpenAI 兼容 / Anthropic 协议，现有供应商可直接复用）。

# 1. 安装 CLI 后交互式配置供应商（含连通性测试）
ocr config provider

# 2. 安装 OCR 驱动版 skill
mkdir -p .agents/skills/open-code-review
curl -o .agents/skills/open-code-review/SKILL.md \
  https://raw.githubusercontent.com/alibaba/open-code-review/main/plugins/open-code-review/skills/open-code-review/SKILL.md

# 3. 也可直接手动调用：完整管线评审（--background 注入业务背景收益最高）
ocr review --audience agent -b "需求背景" --from origin/master --to feat/xxx --format json

输出为结构化 JSON：每条评论含行号、category、severity 与修复建议代码；Agent 会按严重度分组汇报，并在用户要求时自动修复。

形式 ③：CI 流水线（GitHub Action / GitLab CI）

GitHub——官方 Action 一行接入，评论自动以行级形式发到 PR：

mkdir -p .github/workflows
curl -o .github/workflows/ocr-review.yml \
  https://raw.githubusercontent.com/alibaba/open-code-review/main/examples/github_actions/ocr-review.yml

# 在 Settings → Secrets 配置：OCR_LLM_URL / OCR_LLM_AUTH_TOKEN / OCR_LLM_MODEL

GitLab——官方流水线模板同样一条命令，MR 触发、行级 Discussion 回帖：

curl -o .gitlab-ci.yml \
  https://raw.githubusercontent.com/alibaba/open-code-review/main/examples/gitlab_ci/.gitlab-ci.yml

# Settings → CI/CD → Variables：
#   OCR_LLM_URL / OCR_LLM_AUTH_TOKEN（Masked）/ OCR_LLM_MODEL
#   GITLAB_API_TOKEN（可选，api scope；缺省回退 CI_JOB_TOKEN）

内置防刷屏（增量评论、汇总原地更新）、限流退避、fork MR 支持；建议初期「只评论不阻塞」，统计信噪比后再决定是否按 severity 设门禁。

三形式共用：项目规则层

团队规范沉淀在仓库根 .opencodereview/rule.json（随仓库提交，三种形式自动生效）：路径 glob 挂载红线、merge_system_rule: true 与内置语言规则叠加、include 可将默认排除的测试文件拉回评审范围。

{
  "rules": [
    {
      "path": "**/data/local/AppDatabase.kt",
      "merge_system_rule": true,
      "rule": "【红线】改 schema 必须三件事同步：entities/version 更新、新增 Migration 并注册、version +1……"
    }
  ]
}

试点仓库已沉淀 11 条规则 12 处红线（数据库迁移、外部数据单位纪律、架构约束、UI 规范等），逐类文件命中实测通过。

04

总结与建议

结论：建议引入，分阶段推进。工具免费开源（Apache-2.0），唯一成本是 LLM 调用费用且约为通用方案 1/9；本地委托模式零费用即可启动；接入成本一条命令级；试点验证已完成。
阶段内容状态 / 成本
一：本地委托模式 开发者通过编码 Agent 触发委托评审，写码 / 查码独立上下文制衡；规则层沉淀团队红线 已就绪零费用
二：CI 自动评审 PR / MR 触发，先「只评论不阻塞」，统计信噪比与 token 用量；项目规则自动生效 待批准token 按量
三：质量门禁 视试点数据决定是否将 critical 级发现设为合并门禁 视数据—

风险与对策

风险等级对策
代码发送至 LLM 端点（数据安全）中选用国内合规端点或私有化部署模型，需管理层拍板选型
误报骚扰开发者低产品设计即“宁缺毋滥”；低严重度路由、增量去重、初期不阻塞
依赖外部开源项目低Apache-2.0 无商用限制；CLI 可锁版本，规则文件自主可控

试点验证记录（本仓库）

  • CLI v1.9.10 安装、委托模式 preview / rule 命令输出全部正常；
  • 官方 skill 已装入工程，端到端走通一次真实改动的完整评审流程（含单测覆盖核查）；
  • 项目规则层 11 条规则逐类文件实测命中正确，merge 叠加、测试文件 include、声明顺序修正均验证通过。

需要决策的两点

  • 是否批准第二阶段 CI 接入及试点范围（建议先 1~2 个活跃仓库）；
  • LLM 端点选型：复用现有供应商 / 指定国内端点 / 私有化部署——涉及代码数据安全口径。
